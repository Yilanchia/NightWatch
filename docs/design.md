# Nightwatch：多端智能防护网设计

日期：2026-11-10  
状态：设计提案，除明确标注为现有能力外，均未实现。本文用于讨论目标与演进方向，不等于实施授权。

## 1. 愿景与定位

守夜人是一张覆盖用户授权资产的防护网：各节点持续感知本地变化，协调端将分散的线索串成事件，Agent 在授权范围内调查、解释和提出或执行处置，并在处置后继续验证。

目标不是制造一个万能安全工具，而是让用户能回答：**我有哪些资产、哪里正在变化、哪些地方看不到、发生了什么、接下来该做什么、行动是否有效。** 防护网有明确边界，无法保证阻止所有攻击，也无法把未接入或失陷节点的报告当作完整真相。

产品特征：

- **多端协同**：多台主机、服务与账号形成关联，而不是互不相干的告警列表。
- **持续自主**：没有聊天会话或模型时，基础采集、规则、状态与调度仍能工作。
- **证据驱动的智能调查**：Agent 根据目标和已有证据选择受限检查，并区分事实、推断与未知。
- **分级处置**：从自动调查、生成方案到预授权的窄范围自动加固，权限逐级开放。
- **可解释、可恢复**：每次决策、授权、行动和验证都有记录；故障与盲区可见。

第一阶段建议面向用户自己管理的少量 Linux 主机；Windows、手机、路由器与云平台是后续接入候选，具体顺序取决于实际资产和接口权限。手机首先可以作为通知与审批端，不能假设它具备完整主机采集能力。

## 2. 防护网的结构

```text
       用户 / 管理界面 / 手机通知与审批
                       │
        协调端：资产与关系 / 事件 / 策略 / 任务 / 审计
                 │                    │
        确定性检测与编排       可选 Agent / DSH
                 │             计划、查询、解释
                 └─────────┬──────────┘
                     认证与受限通道
            ┌──────────────┼──────────────┐
        主机节点 A      主机节点 B       未来适配器
        本地巡检        本地巡检         云 / 网络 / 服务
        本地证据        本地证据         按实际接口接入
        受限执行器      受限执行器
```

### 2.1 节点

每个节点管理本地采集、基线、规则、发现生命周期、证据和执行状态。节点可离线运行；断网时不声称其他设备正常。节点与协调端恢复连接后同步允许共享的事件，保留原发生时间和接收时间。

写系统配置的执行器应与采集进程分权，按操作和目标授权，不让模型或整个 DSH 宿主以高权限运行。支持能力、平台和权限各不相同，节点需上报能力清单和健康状态。

### 2.2 协调端

协调端维护受管资产、设备身份、关系、策略、事件、任务、通知和审批。它负责将跨节点线索关联为事件，并向节点发出具有范围、期限和审计标识的任务。协调端不能仅因为拥有网络连接就获得节点全部系统权限。

资产关系从用户确认与可靠采集来源建立，例如设备属于哪个环境、服务运行在哪个节点、账号可访问哪些节点；未知关系标为未知，不自动推断成授权事实。第一版用关系表即可，图数据库不是前提。

### 2.3 DSH 与 Agent

延续现有方向：Nightwatch 核心负责调度、证据、确定性规则、策略和执行；DSH 是可选的插件与模型交互宿主。模型可以生成调查计划、请求受限工具、解释证据和拟定提案，但不能直接改写事实、策略、审批或执行结果。

独立核心已有无模型 `tick`；专用 DSH 宿主组合、工具实际能力校验、模型数据出口控制仍需实现和验证。不要把工具名过滤、提示词或现有 guard 当作操作系统沙箱。

## 3. 从发现到处置的闭环

1. **感知**：节点按计划或事件触发采集，记录来源、时间、版本、结果与健康状态。
2. **发现**：规则或人工线索形成发现；事实、规则结论和模型推测分别标识。
3. **关联**：协调端按设备、账号、服务、时间窗和证据建立事件。关联有依据和置信度，不把时间相近直接说成因果。
4. **调查**：Agent 为事件提出目标，选择允许的只读检查，读取结果并调整下一步；每轮受工具清单、设备范围、次数、时间和数据量约束。
5. **判断**：输出已确认事实、可能解释、反证、缺口、风险及建议；证据不足时停止并升级给人。
6. **处置**：按策略生成提案、请求审批或执行已预授权动作。
7. **验证与复盘**：重新读取目标状态并记录业务影响、执行结果及回滚状态；持续观察复发。动作成功不等于风险已经消除。

模型不可用时，规则、持久化与通知继续工作，调查标记为待处理或退回确定性流程。模型输出错误、格式不合规、循环、超预算或工具失败时应停止该调查，不扩大权限。

## 4. 覆盖范围与分期

| 防护面 | 关注内容 | 建议阶段 |
| --- | --- | --- |
| 资产与健康 | 已接入设备、能力、最后在线、采集盲区 | 第一阶段 |
| 主机暴露面 | 监听端口、进程与服务归属、SSH 配置与公钥变化 | 第一阶段 |
| 账号与登录 | 登录事件、授权账号、同一身份跨主机异常 | 第二阶段，依赖平台数据和授权 |
| 系统完整性 | 关键配置、启动项、敏感文件变化 | 第二阶段，限定路径和采集开销 |
| 服务与漏洞 | 软件清单、版本、证书、已知漏洞关联 | 后续，明确数据源与误报处理 |
| 网络与云 | 网络设备、云资产、身份与配置事件 | 后续，按设备及供应商接口评估 |
| 备份与恢复 | 备份新鲜度、失败和恢复演练 | 先检查状态，恢复演练单独授权 |

每个检查需声明支持平台、所需权限、频率、数据来源、资源预算和已知盲区。采集失败、未配置、设备离线、数据过期分别展示；没有告警不代表已覆盖。osquery、Sigma 等是候选能力，需先验证平台兼容、字段映射、规则语义与性能，不能假设接入后即可覆盖全部场景。

## 5. 多端通信与信任

### 5.1 设备接入

用户显式登记设备，完成双向认证并确认设备身份与所属环境；节点持独立凭据，可轮换和吊销。传输采用经过验证的加密与认证机制，具体协议和证书方案在原型验证后选定，不预设现有其他项目通道已满足需求。

设备能力和授权应分别记录：节点能做某事，不代表协调端或 Agent 被允许要求它做。任务携带目标、允许动作、参数范围、有效期与唯一标识；节点本地再次执行策略，不能只依赖中心判断。

### 5.2 同步与离线

默认在节点保留原始证据，协调端接收必要的结构化发现、健康信息和经允许的摘要。跨端调查如需进一步证据，按明确用途、范围和授权获取；敏感信息在采集和导出前最小化。原文、秘密和用户数据不默认发送给云模型。

每个节点事件携带设备 ID、递增序号、事件 ID、发生时间、接收时间与版本；接收端去重，断线后按游标重传。重复投递可发生，消费者必须幂等；不承诺跨故障恰好一次。时钟偏差、缺失序号、队列积压、存储不足都应可见。

状态冲突保留来源并标记待复核；节点离线期间不补造观测。证据保存期限、加密、备份、删除与导出策略需由用户确定；仅追加日志和摘要哈希不等于防篡改，失陷节点可能伪造或删除本地证据。以后可评估远端审计副本及完整性校验，并说明其信任边界。

### 5.3 审批与远程任务

审批绑定设备、资源、具体变更、原状态指纹、策略版本、批准者、到期时间和一次性任务 ID。节点执行前重新检查身份、授权、目标状态和有效期；条件变化、超时或撤销时拒绝并重新提案。离线审批是否允许、超时后如何处理由策略明确规定，默认拒绝高影响动作。

## 6. 自动加固与安全控制

| 级别 | 允许的行为 | 准入条件 |
| --- | --- | --- |
| L0 观察 | 计划采集、确定性规则和报告 | 授权设备、只读权限、资源限制 |
| L1 调查 | Agent 选择白名单只读检查 | 目标、范围、预算和审计明确 |
| L2 提案 | 生成具体变更及风险、验证和回滚 | 证据充分；未知项和依赖可见 |
| L3 预授权执行 | 仅对明确设备和动作自动执行 | 用户预先批准的策略、状态前置检查、可靠验证与回滚、限频和熔断 |
| L4 单次审批执行 | 高影响或超出预授权范围的动作 | 绑定具体提案的人工批准，执行前重新校验 |

等级描述授权方式，不意味着 L3 的所有动作都比 L4 安全。远程登录、网络隔离、账号禁用等操作可能造成失联，需要带外恢复路径与单独评审。找不到可信验证或回滚手段时保持提案，不自动执行。

执行器只接受版本化、参数受限的动作定义，不接受模型生成的任意 shell。执行记录包含操作人/策略、提案与任务、目标、执行前状态、结果、验证和回滚结果；同一任务重复投递不得重复执行。审计不可用、授权不明确、节点状态不可信、条件失效或超过预算时拒绝动作。

当前代码中的修复提案为 `executable: false`，执行工具默认不注册；不应把已有执行器当作自动加固已完成。首次开放任何写操作前需独立评审、隔离环境测试和真实恢复演练。

## 7. 首个跨端闭环：SSH 公钥异常

**建议场景**：两台授权 Linux 主机 A、B；用户明确建立 SSH 公钥基线及账号与设备关系。

1. A 检测到新的授权公钥，记录指纹、采集时间、基线版本及观测质量；无法读全时标记盲区。
2. 协调端创建事件，按已确认关系查询 B 是否有同一指纹或相关账号变化；不上传公钥正文或私钥。
3. Agent 在有限预算内查询两端的变更时间和允许读取的登录线索，输出证据及其他解释。关联不等于入侵，离线或缺失日志不能写成“未发现异常”。
4. 用户可将变化确认成合法变更，或要求生成撤销提案。确认合法与更新基线是独立、可审计的动作。
5. 在隔离测试环境验证一种受限、可恢复的撤销动作；生产默认仅提案。未来启用时须验证账号、文件指纹、另一条可用登录或带外恢复条件，并绑定审批。
6. 执行后重新采集并记录结果；观察复发和其他设备状态。某端离线时事件保持未完成或部分完成。

验收应覆盖：正常和等量替换、合法变更、权限不足、重复消息、节点离线重连、撤销审批、执行前状态变化、执行失败、回滚失败和模型不可用。至少一条完整事件能从展示追溯至各节点证据与动作记录。

## 8. 路线图与验收

### M0：可信单机基础

现有端口、SSH、备份采集、证据日志、规则、生命周期与无模型 `tick` 是基础。先修复不完整基线、不同规则的恢复条件、`partial` 退出状态与 CLI/宿主配置不一致；核对 SSH 实际生效配置的读取边界。补持久调度、最近成功时间、下次运行与盲区查询。

**验收**：一台 Linux 测试机连续 7 天，成功与失败均有记录；中断和重启可解释；模型不可用仍能巡检；恢复与复发依据证据判断；数据库重建一致。7 天是最低观察目标，不代表生产安全认证。

### M1：双节点与中心只读联动

实现设备登记、认证、能力与健康上报、受限同步、事件去重和跨端只读查询；完成上面的 SSH 场景至调查结果，写操作关闭。

**验收**：两台节点支持离线重连、重复投递、吊销设备、中心故障与权限不足；每条跨端结论可追溯，不能查询未授权设备；原始数据和模型出口符合配置。

### M2：有预算的智能调查

在有限工具上实现计划、执行、观察、调整、停止和人工升级，记录模型、工具版本、输入摘要、行动与结果。保留无模型规则路径。

**验收**：针对正常变更、真实异常、缺失证据、恶意日志文本和模型失败的测试样本，检查结论引用、停止条件、无越权工具调用和人工接手。先建立评估集和误报、漏报、调查成本指标，不预设准确率。

### M3：受限加固试点

在隔离环境实现一个明确定义的动作及审批、前置检查、验证、回滚、审计和熔断；观察运行后再评审预授权自动执行。不要同时扩大动作类型、设备范围与权限。

**验收**：正常、拒绝、撤销、过期、重放、断网、状态竞争、执行和回滚失败均有结果；失去恢复能力时不会继续执行；经过真实恢复演练。

### M4：扩展防护网

按真实资产需求添加 Windows、云或网络适配器、更多检测与处置。每接一类先定义权限、数据来源、覆盖盲区、性能和验收，再选择已有成熟组件或自行实现。

## 9. 待确认的产品决策

1. 首批实际资产：两台 Linux、Windows 加 Linux，还是其他组合？由此确定采集与部署方式。
2. 协调端部署在用户本机、专用服务器还是其他位置？中心故障与备份要求随之变化。
3. 手机首期是否只负责通知和审批，是否需要离线审批？
4. 原始证据、摘要与模型处理分别允许保留和传输多久、到哪里？
5. 哪些动作可以预授权自动执行，哪些必须逐次确认？哪些设备永不自动修改？
6. 首个试点场景是否采用 SSH 公钥异常，还是用户更关心端口暴露、账号登录或其他风险？

## 10. 与现有项目的关系

当前实现是防护网中的**单机节点原型**，不是完整多端系统。现有代码提供采集、日志、规则、发现生命周期、报告、时间线和受限工具入口；中心协调、节点身份与同步、主动调查、多端审批和自动加固均属于待设计或待实现能力。

本文更新产品目标与后续优先级；当前实现与本文的差距按版本路线推进，历史构思不自动视为现状。[项目入口](../README.md)。
